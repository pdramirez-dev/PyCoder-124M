# Training Guide

This guide covers PyCoder-124M training on NVIDIA CUDA, Apple MPS, and CPU.
Run commands from the repository root. Shell examples use Bash, including Bash
inside WSL on Windows.

If training is already running, leave its tokenizer, processed data, and configuration
unchanged. Use the monitoring commands below to inspect it.

## 1. Install the environment

Use Python 3.12 and install the project dependencies:

```bash
uv sync
```

For NVIDIA hardware, check both the driver and the project environment:

```bash
nvidia-smi
uv run python -c 'import torch; print("PyTorch:", torch.__version__); print("CUDA available:", torch.cuda.is_available())'
```

A working `nvidia-smi` does not by itself prove that PyTorch can use CUDA.

## 2. Detect hardware and choose a configuration

Inspect hardware without starting training:

```bash
uv run python -m pycoder.hardware
```

The advisor automatically selects CUDA, then MPS, then CPU. It reports system RAM
and CUDA VRAM, and suggests training settings for **model_124m.yaml with context
length 1024**. RAM and CUDA VRAM are separate; Apple MPS uses unified memory.
The reported RAM is what the current environment exposes, which may differ from
physical host RAM under WSL or a virtual machine.

To inspect a specific backend or save a suggested configuration:

```bash
./run.sh --suggest-profile --device cuda
./run.sh --suggest-profile --device cuda --output configs/train_local.yaml
uv run python -m pycoder.hardware --device mps
```

The output file must not already exist. Suggestions consider currently free CUDA
VRAM, so other GPU processes can affect the recommendation. They are conservative
heuristics, not guarantees that training will fit.

| Backend | Default configuration used by run.sh | Precision | Batch | Accumulation |
|---|---|---|---:|---:|
| CUDA | configs/train_124m_cuda.yaml | bfloat16 | 1 | 64 |
| MPS | configs/train_124m.yaml | float32 | 4 | 16 |

`run.sh` defaults to CUDA and accepts `--device cuda` or `--device mps`.
The fixed CUDA configuration requires bfloat16 support; the advisor instead
suggests float16 when the CUDA device does not support bfloat16. CPU training
uses the Python entry point directly.

## 3. Prepare data for a new run

Skip this step when resuming. Do not regenerate a tokenizer or dataset used by an
existing checkpoint. The demo corpus is for testing and is insufficient for useful
124M training.

Use a corpus whose licensing and provenance you have reviewed. See
[datasets.md](datasets.md) for the existing dataset workflow. For a corpus already
stored in `data/raw`, prepare matching tokenizer and dataset splits:

```bash
uv run python scripts/train_tokenizer.py \
  --source data/raw --vocab-size 50304 --validation-fraction 0.05 --seed 42
uv run python scripts/prepare_dataset.py \
  --source data/raw --validation-fraction 0.05 --seed 42
```

Both commands must use the same source, filters, seed, and validation fraction.
Their default outputs are `data/tokenizer.json` and `data/processed/`. The latter
contains `train.bin`, `val.bin`, and `manifest.json`. These commands write generated
artifacts, so use separate output paths for independent experiments when needed.

The production model has vocabulary capacity 50,304. The tiny model has capacity
512; it cannot use a tokenizer whose vocabulary exceeds that capacity.

## 4. Start training

For an NVIDIA GPU using the provided CUDA settings:

```bash
./run.sh --device cuda --checkpoints checkpoints/cuda --logs logs/cuda
```

To use a configuration generated by the advisor:

```bash
./run.sh --device cuda --config configs/train_local.yaml \
  --checkpoints checkpoints/local --logs logs/local
```

For Apple Silicon:

```bash
./run.sh --device mps --checkpoints checkpoints/mps --logs logs/mps
```

To use CPU explicitly, select a float32 configuration through the Python script:

```bash
uv run python scripts/train.py --model configs/model_124m.yaml \
  --config configs/train_124m.yaml --device cpu \
  --checkpoints checkpoints/cpu --logs logs/cpu
```

CPU training of the full model can be very slow. The MPS configuration also needs
substantial unified memory; consult the advisor for a smaller batch when needed.

Use separate checkpoint and log directories for different experiments. The
checkpoint file `latest.pt` is replaced during training; historical checkpoints
are not kept automatically.

The startup message should show `Device: cuda`, `Device: mps`, or `Device: cpu`.
It appears after model allocation and any checkpoint loading, so an allocation
failure can happen before this message is printed.

## 5. Understand the main parameters

| Parameter | Effect |
|---|---|
| batch_size | Sequences processed in each forward/backward pass; larger values usually need more memory. |
| gradient_accumulation | Passes accumulated before one optimizer update. |
| precision | float32 for CPU/MPS/CUDA; float16 or bfloat16 for supported CUDA hardware. |
| max_steps | Total optimizer updates, including updates already completed when resuming. |
| learning_rate | Peak learning rate used by the schedule. |
| warmup_steps | Initial updates used for learning-rate warmup. |
| eval_interval / eval_batches | Evaluation frequency and number of validation batches. |
| checkpoint_interval | Number of optimizer updates between checkpoint saves. |

The effective token count per optimizer update is:

```text
batch_size × gradient_accumulation × context_length
1 × 64 × 1024 = 65,536 tokens
```

The provided CUDA and MPS configurations preserve this count. With 1,526 updates,
they process roughly 100 million training tokens. The stream cycles through the
dataset when exhausted, so this does not imply 100 million distinct tokens.

## 6. Monitor a running job

For NVIDIA GPU utilization, memory, temperature, and power:

```bash
watch -n 1 nvidia-smi
```

For Linux/WSL system RAM and swap:

```bash
free -h
```

For losses, learning rate, and allocated GPU memory:

```bash
uv run tensorboard --logdir logs
```

Open the address printed by TensorBoard. Metrics include `loss/train`,
`loss/validation`, `learning_rate`, and `memory/cuda_allocated_bytes` or
`memory/mps_allocated_bytes`. PyTorch allocated memory differs from total driver
memory shown by `nvidia-smi`, which also includes caching and runtime overhead.

On Windows, Task Manager's 3D chart may not show CUDA compute activity. Use
`nvidia-smi` as the direct check. High CPU usage can coexist with active GPU training.
A short utilization sample does not establish long-term throughput or temperature.

## 7. Stop and resume

Press **Ctrl+C once** to request a checkpoint after the current optimizer step.
With gradient accumulation 64, finishing that step can take time. Wait for the
process to exit rather than killing it immediately.

Resume the provided CUDA configuration:

```bash
./run.sh --device cuda --resume checkpoints/cuda/latest.pt \
  --checkpoints checkpoints/cuda --logs logs/cuda
```

For a custom profile, pass the same configuration file again:

```bash
./run.sh --device cuda --config configs/train_local.yaml \
  --resume checkpoints/local/latest.pt \
  --checkpoints checkpoints/local --logs logs/local
```

Resuming requires identical model and training configuration values and the same
training-data hash. Preserve the tokenizer and validation split too. Changing
batch size, accumulation, precision, or even max_steps fails the configuration
check. An old float32 checkpoint cannot resume using a new bfloat16 profile.
Do not bypass this check to change hardware profiles.

The checkpoint includes model weights, optimizer, scheduler, scaler, random states,
and stream position. Load only trusted checkpoints. For reproducibility, retain
the same hardware, backend, and software versions as well.

## 8. Evaluate and generate code

Evaluate a saved checkpoint with a small evaluation batch:

```bash
uv run python scripts/evaluate.py checkpoints/cuda/latest.pt --batch-size 1
uv run python scripts/generate.py checkpoints/cuda/latest.pt \
  --prompt 'def fibonacci(n):' --max-new-tokens 100
```

These scripts select the available device automatically. Evaluation currently
uses float32, so its memory use differs from mixed-precision training. Generation
uses `data/tokenizer.json` by default; pass `--tokenizer` for another tokenizer.
Validation loss and perplexity measure prediction quality, not whether generated
Python is functionally correct. Running evaluation alongside training also consumes
additional GPU memory.

## 9. Troubleshooting

| Symptom | Action |
|---|---|
| PyTorch is not linked with support for mps devices | On NVIDIA, use `--device cuda`; MPS is for Apple GPUs. |
| CUDA unavailable | Check `nvidia-smi` and CUDA availability inside the same uv environment used for training. |
| CUDA out of memory | For a new run, lower batch size and increase accumulation to preserve tokens per update. Close other GPU workloads. An existing checkpoint requires its original configuration. |
| CUDA device does not support bfloat16 | Generate a device profile; the advisor selects float16 for CUDA without bfloat16 support. |
| Checkpoint configuration differs | Restore the original model and training configuration values. |
| Training dataset differs from checkpoint | Restore the original processed training data. |
| Tokenizer vocabulary exceeds model vocabulary | Match the tokenizer to the model; do not regenerate artifacts for an active run. |
| GPU chart appears idle | Inspect nvidia-smi while the process is running and confirm the training command uses CUDA. |

For code changes, run the repository checks:

```bash
uv run pytest -q
uv run ruff check src scripts tests
```
